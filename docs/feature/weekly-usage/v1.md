# Weekly AI usage guard — release candidate

**Status:** Implemented on `feature/staging-v1` but **not shipped**. The additive migration has not been applied to any hosted database; no production deploy or production verification has occurred. Treat this as a release candidate only.

## Product policy

- Each account receives **500 credits per UTC week**.
- The week begins Monday 00:00 UTC. The server/database returns the precise next reset timestamp; the browser only localizes it for display.
- Logical modes stay `Fast`, `Balanced`, `High`: respectively **1, 3, and 6 credits per generation**.
- Weights are Nibie product-policy units for cost control and abuse prevention, not actual provider prices, token counts, or dollar values. Server-side routing and provider/model identifiers remain private.
- This is free-product usage protection and usage measurement—not a paid plan. There is no Stripe, billing, checkout, subscription, purchased credit, or upgrade flow.

## What is charged

One reservation is made for one newly claimed assistant generation, immediately before the provider call, after request validation, authentication, ownership checks, saved-message/context loading, and the idempotent generation claim.

- Send, Retry, Regenerate, and Edit/resend count when they create a new provider-backed generation.
- A generation stopped after the provider stream has been established stays charged.
- A failure before the provider stream is established attempts an atomic, idempotent release. This includes an error response from stream setup.
- A replay that skips provider generation, navigation, authentication, history reads, model selection alone, Room actions, Pins, file upload alone, Workbench operations, and other database-only work do not count.
- A quota rejection happens before the provider call, is not charged, and returns HTTP 429 with stable code `WEEKLY_USAGE_LIMIT` plus the server's reset timestamp.

`weekly_usage_reservations` uses the assistant message UUID as a unique generation key. Reservation plus account/week counter update happen in one database function/transaction; account-row locking and a conditional upsert prevent concurrent tabs/conversations from exceeding 500. Replays of the same generation key do not add credits twice.

## Data and access

Migration `drizzle/0010_weekly_ai_usage.sql` adds owner/week aggregate counters and a generation-keyed reservation/release ledger. Migration `drizzle/0017_weekly_usage_limit_500.sql` raises the ceiling from 100 to 500 credits without resetting existing `credits_used` rows. Both tables have forced RLS. Clients receive SELECT on the owner-scoped aggregate only; direct writes and direct ledger reads are denied. The browser never submits a cost, week, or remaining balance.

The narrow reservation/release functions are `SECURITY DEFINER`, unlike the existing user-owned chat RPCs. This is intentional: granting the authenticated role direct mutation rights would let a user forge or reset their quota. The functions derive ownership exclusively from `auth.uid()`, use a fixed empty `search_path`, fully qualify database objects, validate that the generation is an active assistant message for that owner, and expose only authenticated execution. The read-only usage function is `SECURITY INVOKER`. No service-role credential or privileged runtime client is added.

## UI and events

Settings → General shows remaining weekly credits and the server-supplied reset time, with the three mode weights. The model picker keeps only the three logical modes and shows their credit weights. The composer does not issue a usage preflight; Send makes only its existing chat request. An exhausted response is rendered from its machine-readable code and human-readable reset time. No billing or upsell UI is added.

Structured events record reservation accepted/rejected with request ID, logical mode, credits charged/remaining, and reservation latency. They do not include user IDs, prompt content, tokens/secrets, or provider credentials.

## V1 limitations and rollout checks

- Weekly credits remain a weighted request allowance (not invoice dollars). **PR A — AI Cost & Usage Guard** adds a separate server-enforced USD spend ceiling (`AI_SPEND_LIMIT_USER_DAILY_USD`, `AI_SPEND_LIMIT_GLOBAL_HOURLY_USD`) plus provider token accounting and `POST /api/cron/reconcile-usage` for stale holds.
- If the app process disappears after the reservation commits but before it can learn whether the provider established a stream, the reservation may remain charged until reconcile runs.
- No production migration, deployment, or production data has been run/changed for this candidate. Apply it only through the reviewed release migration process, then verify reservation concurrency, RLS, quota rejection, stop behavior, reset timestamp, and mobile layout in the deployed environment before calling it shipped.
- Candidate checks run against isolated loopback Postgres and local preview flows; they do not establish hosted Supabase schema-cache/RPC behavior or production provider first-token latency.
