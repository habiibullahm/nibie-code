# Files V1

Files V1 lets a room hold a few text files and lets a person attach one of those files to a single message. It is not search, and it is not retrieval over every file in the room.

## Supported formats

| Format | Stored type |
| --- | --- |
| `.txt` | `text/plain` |
| `.md` | `text/markdown` |
| `.csv` | `text/csv` |

The server accepts a file only when the extension, the declared type, and the bytes agree. A matching extension is not enough. `application/octet-stream` or an empty type is accepted only after the bytes are confirmed to be UTF-8 text with no binary signature.

PDF is deferred. There is no OCR, no image reading, and no DOCX or XLSX support.

## Limits

- Maximum upload size: **5 MB**
- Maximum extracted text stored on the row: **24,000 characters**
- Maximum file text placed in one model request: **1,500 estimated tokens**
- Maximum files in one room: **20**
- Maximum files attached to one message: **3**

Text past the character limit is stored truncated. Text past the token budget is shortened again for that request. The current user message is kept ahead of file text.

## Storage

Files use the private Supabase Storage bucket `room-files`. The app does not add a second storage system.

Object keys are built on the server:

```text
<user-id>/<room-id>/<file-id>/<file-id>.<ext>
```

The original filename is display metadata only. It is sanitized and is never the authorization path. The owner id comes from the signed-in session.

Migration `drizzle/0006_room_files.sql` creates `room_files`. When the database has Supabase's `storage` schema, the same migration creates the private bucket and owner-folder policies. A plain Postgres test database skips that block.

## Security

- Select, insert, and delete policies on `room_files` require `user_id = auth.uid()`.
- There is no update policy and no grant for update.
- Storage policies allow select, insert, and delete only inside the caller's first folder.
- Ordinary file operations use the cookie-bound Supabase client. They do not use the service role.
- A room delete removes stored objects before the room row. If storage deletion fails, the room stays.
- A file delete removes the object first. If that fails, the row stays, and the product does not say the file is gone. If the object is gone and the row delete fails, the error says the record is still there.
- Extracted text is not written to logs.

## Context

Room files are not added to every message.

When a person checks a file in a room thread, that request includes the extracted text as **File context**. The text is untrusted data. It sits in the data block, after room instructions and before the thread summary. It is not part of the product-policy prompt.

Order when a file is selected:

1. Product rules
2. Profile
3. Room
4. Pins, once that separate work is integrated
5. File context
6. Thread summary and recent messages
7. The current request

The current request stays the last user message. Pins are not implemented on this branch. The file block is placed so a later pins block can sit between the room and the file without a second context builder.

Regenerate in the same browser session resends the file ids chosen for that message. After a full refresh, that selection is only kept in session storage for the tab. It is not a separate database link yet.

## Unsupported

Embeddings, pgvector, semantic search, chunk retrieval, RAG, OCR, image understanding, DOCX, XLSX, Google Drive, Dropbox, URL crawling, web scraping, agent tools, background indexing, and file summaries from extra model calls are out of scope.
