# Room Files V2

Room Files V2 stores private source files for a room. A person can select files for full context, and Nibie can retrieve relevant lexical excerpts from that room for a question. This is deterministic PostgreSQL full-text search, not semantic search.

## Supported formats

| Format | Stored type |
| --- | --- |
| `.txt` | `text/plain` |
| `.md` | `text/markdown` |
| `.csv` | `text/csv` |
| `.json` | `application/json` |
| `.pdf` | `application/pdf` |
| `.docx` | `application/vnd.openxmlformats-officedocument.wordprocessingml.document` |
| `.ts`, `.tsx` | `text/typescript` |
| `.js`, `.jsx` | `text/javascript` |
| `.py`, `.java`, `.go`, `.rs`, `.sql`, `.html`, `.css`, `.yaml`, `.yml`, `.xml` | canonical text MIME type |

The server accepts a file only when the extension, declared type, and bytes agree. A matching extension is not enough. UTF-8 text and source files are decoded without changing line breaks. PDF extraction is text-only, reads at most 50 pages and 24,000 characters, and rejects PDFs over 100 pages; locked, corrupt, or scanned/no-text PDFs fail clearly. DOCX extraction reads only `word/document.xml`, never executes macros or fetches relationships, and enforces archive entry and decompressed size limits.

There is no OCR, image reading, XLSX, or PPTX support.

## Limits

- Maximum upload size: **5 MB** (larger than the 4 MB chat-attachment limit)
- Maximum extracted text stored on the row: **24,000 characters**
- Maximum file text placed in one model request: **1,500 estimated tokens**
- Maximum files in one room: **20**
- Maximum explicitly selected files per message: **3**
- Lexical retrieval returns at most **5** matching chunks after excluding explicitly selected files; distinct chunks from one file can both be returned.

Text past the character limit is stored truncated with an explicit partial-source marker. Chunks are 2,400 characters with 240-character overlap. Text past the token budget is shortened again for that request. The current user message is kept ahead of file text.

## Storage

Files use the private Supabase Storage bucket `room-files`. The app does not add a second storage system.

Object keys are built on the server:

```text
<user-id>/<room-id>/<file-id>/<file-id>.<ext>
```

The original filename is display metadata only. It is sanitized and is never the authorization path. The owner id comes from the signed-in session.

Migration `drizzle/0007_room_files.sql` creates `room_files`; additive migration `drizzle/0012_files_v2_lexical.sql` widens supported formats and creates owner-scoped lexical chunks and search. When Supabase's `storage` schema exists, the initial migration creates the private bucket and owner-folder policies. A plain Postgres test database skips that block.

## Security

- Select, insert, and delete policies on `room_files` require `user_id = auth.uid()`.
- There is no update policy and no grant for update.
- Storage policies allow select, insert, and delete only inside the caller's first folder.
- Ordinary file operations use the cookie-bound Supabase client. They do not use the service role.
- A room delete removes stored objects before the room row. If storage deletion fails, the room stays.
- A file delete removes the object first. If that fails, the row stays, and the product does not say the file is gone. If the object is gone and the row delete fails, the error says the record is still there.
- Extracted text is not written to logs.
- Chunk records cascade with their source file and room; row-level security and the search function both scope results to the authenticated owner and current room.

## Context

Room files are not added to every message.

When a person selects a file in a room thread, the request includes its extracted text. Otherwise, lexical matches from the current user message can add up to five relevant chunks from the current room. Automatic retrieval is best-effort; explicit selection remains strict. File text is untrusted data and never enters the product-policy prompt. Context includes the filename and a partial-source marker when extraction was truncated.

Order when a file is selected:

1. Product rules
2. Profile
3. Room
4. Room pins
5. Explicitly selected files, then automatic lexical excerpts that did not match those files
6. Thread summary and recent messages
7. The current request

The current request stays the last user message. Room instructions and pins stay outside file context; file contents remain untrusted data. Regenerate in the same browser session resends the file ids chosen for that message. After a full refresh, that selection is only kept in session storage for the tab. It is not a separate database link yet.

## Unsupported

Embeddings, pgvector, semantic search, OCR, image understanding, XLSX, PPTX, Google Drive, Dropbox, URL crawling, web scraping, agent tools, and file summaries from extra model calls are out of scope.
