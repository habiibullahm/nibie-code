# Files V3 Hybrid Search

Status: implemented on `feat/files-v3-hybrid-retrieval`. Live OpenAI relevance for the **0.55** semantic-only gate remains fixture-calibrated only (conservative default). [Files V2](v2.md) remains the baseline for extraction, storage, context budgets, and selected files.

V3 retains the V2 lexical query builder, simple-text GIN index, SQL ranking, and default five-result RPC behavior. The chat path requests a bounded pool of ten lexical candidates and ten cosine candidates, fuses positions using Reciprocal Rank Fusion (`k = 60`), applies deterministic reranking, and returns at most five automatic excerpts. Explicitly selected files precede automatic excerpts and are excluded before the final five, so their chunks are never duplicated in context.

The existing 2,400-character chunker runs once per upload. Upload inserts lexical chunks first (with stable ids), then best-effort fills vectors via the scoped fill RPC. Embedding uses `text-embedding-3-small`, `dimensions: 512`, and float encoding on those same chunks; no second chunk table or chunker is introduced. This follows the [official OpenAI embedding API contract](https://developers.openai.com/api/reference/resources/embeddings/methods/create). The server reads `OPENAI_API_KEY` and calls the fixed official `/v1/embeddings` endpoint; embedding settings do not depend on the selected chat provider or mode. Inputs and provider responses are never logged. Batches are at most 20 texts of at most 3,000 characters. Timeouts: **1.5s** query embed, **2s** upload embed, **5s** backfill; no automatic retries.

An absent key skips semantic work without treating it as a failure. Failed or timed-out embed/RPC semantic attempts degrade to lexical-only retrieval and emit `logWarn("room_file.search.failed", { stage: "room_file_search_semantic" })` (lexical failures keep `stage: "room_file_search"`). Both pools run concurrently when a key is present; Supabase RPC requests carry a two-second abort deadline. Empty or malformed search responses cannot fail the reply. Existing strict validation of selected files remains in place.

## Ranking and rejection

RRF adds `1 / (60 + rank)` once per distinct chunk per pool. Reranking gives exact identifier evidence priority, then adds a small bounded cosine evidence bonus (`0.005 * max(0, min(1, similarity) - 0.55)`) to the fused score. Distinct lexical-term coverage resolves remaining ties, followed by a stable file/chunk key. There is no model reranker or query rewriting.

Identifier queries (snake case, camel case, filenames/paths, function-call names, alphanumeric symbols, uppercase constants, or backtick names) require all detected identifiers to occur with token boundaries in the candidate filename/content. Fuzzy alternatives for another symbol are rejected, including an unknown-symbol question. Matching is case sensitive. Plain sentence-ending punctuation is not an identifier. This conservative rule can reduce recall for questions comparing several symbols stored in separate chunks.

A semantic-only candidate requires finite cosine similarity of at least **0.55**. Lexical candidates retain V2 behavior. The threshold is a conservative initial gate tested with synthetic vectors, not a calibrated OpenAI relevance probability. The fixture evaluation cannot establish production semantic accuracy or guarantee zero false positives on arbitrary real documents. Live labeled validation should calibrate this threshold when credentials are available. Automatic context remains untrusted and subject to the existing file token budget.

## Database and isolation

Additive migration `0014_files_v3_hybrid.sql` follows every V2 migration and adds a nullable 512-dimensional vector, a nonzero-vector check, an HNSW cosine index, and owner-scoped semantic/backfill RPCs. It respects an existing vector extension schema, including Supabase's `extensions`, without relocating the extension. The authenticated role receives schema USAGE for the extension type and operators. A fresh installation creates the extension in `public`. The migrator requires permission to install pgvector when absent.

Search uses the cosine distance operator directly in its ordered bounded query. The semantic RPC is created with `search_path = ''` only; optional HNSW GUCs (`ef_search`, `iterative_scan`, `max_scan_tuples`) are applied afterward with `ALTER FUNCTION` and ignored when the installed pgvector build does not support them, so migration cannot fail CREATE on unrecognized settings. ANN retrieval can still return fewer than ten candidates; it never broadens the authorization scope. Small fixtures may use PostgreSQL's sequential plan instead of HNSW.

All RPCs are `SECURITY INVOKER` with an empty search path, explicit extension qualification, no PUBLIC execute grant, and `authenticated` execute grants. Existing forced RLS stays enabled. Searches require both the current authenticated user and the specified current Room, and join to the matching source file. No service role or external vector store is used.

Only `embedding` receives a new column-level update grant. The update policy permits owner rows whose embedding is still NULL; other chunk columns cannot be edited, and existing vectors cannot be overwritten. Source-file deletion still cascades through the existing chunk foreign keys.

## Bounded backfill

`backfillRoomFileEmbeddings(client, roomId, limit)` in `lib/files/search.ts` is the bounded server maintenance operation. It reads at most 20 existing missing-vector chunks in deterministic id order, embeds that batch, and calls the scoped fill RPC. It returns the actual number of rows filled. The authenticated, same-origin `POST /api/rooms/{roomId}/files/backfill-embeddings` endpoint invokes one batch per request using the caller's cookie-bound Supabase client; no service role is used and no content is returned. Repeat requests deliberately until `{ "processed": 0 }`. A provider failure returns a generic 503 without writing vectors; a later request can retry.

The route applies a **process-local** guard: at most one in-flight backfill per authenticated user and at most **six** started batches per user per rolling 60 seconds (HTTP 429 when exceeded). This limits OpenAI spend on a single instance; it is not a shared global quota across serverless isolates. Concurrent calls on different instances may still duplicate provider work, but conditional updates and RLS prevent overwrites. Already-filled chunks make no further embedding calls.

## Local validation and fixture evaluation

Run `npm test`, `npm run typecheck`, `npm run lint`, `npm run test:integration:local`, and `git diff --check`. The local integration runner uses `pgvector/pgvector:pg17`, container `nibie-v3-test-postgres`, and loopback port **55433** for the dedicated `nibie_ai` database. It cleans up its own container afterward. Integration tests also exercise a preinstalled `extensions`-schema vector extension, Room/user isolation, column update permissions, idempotent bounded fill, cosine retrieval, and cascading deletion.

Run `npm run test:files-v3:eval` for the reproducible, explicitly **fixture-based** comparison. Hand-authored normalized 512-dimensional fixture vectors stand in for embeddings; the lexical evaluator uses a documented simple-token approximation, while separate integration tests execute the real V2 SQL. The corpus contains deployment/auth/cache paraphrases, exact/missing identifiers, repeated-keyword distractors, and unrelated no-answer queries. This is a ranking and rejection regression suite, not a live OpenAI benchmark.

The required document is `The deployment pipeline releases the backend service after validation.` and query is `How is the backend shipped to production?`. Hybrid retrieves it at rank 4; hybrid plus reranking retrieves it at rank 1.

| Mode | Recall@5 | MRR | No-answer false positives |
| --- | ---: | ---: | ---: |
| Lexical approximation | 0.25 | 0.25 | 0/3 |
| Semantic fixture vectors, ungated baseline | 0.75 | 0.75 | 3/3 |
| Hybrid with rejection gates | 1.00 | 0.8125 | 0/3 |
| Hybrid + deterministic rerank | 1.00 | 1.00 | 0/3 |

Recall and MRR use the four answerable cases. No-answer false positives count a query that returns any context. The printed report includes each query's first relevant rank, case category, returned count, and local candidate-ranking/fusion elapsed time. One observed fixture run took **9.93 ms lexical, 1.17 ms semantic, 4.19 ms hybrid, and 0.86 ms hybrid+rerank** across seven queries per mode; these local times vary with host load and exclude database and network calls. **Live embedding/network latency, live OpenAI relevance, and production database latency are unmeasured** because this environment has no API key. No external data backfill was run.

OCR, web search, agents, model reranking, query rewriting, external vector databases, and a citations UI remain outside this change.
