# Chat Attachments V1

Chat attachments let a person attach files to a message they send in a chat. Nibie reads the text of those files and answers from it in that conversation, including in follow-up messages.

A chat attachment belongs to one user message in one conversation. It is not Room knowledge.

## Chat attachment or Room file

| | Chat attachment | Room file ([Files V2](../files/v2.md)) |
| --- | --- | --- |
| Belongs to | One user message in one conversation | A Room |
| Added from | The composer "+" → **Upload from device** | The Room page |
| Used in | That conversation only: the message it was sent with and later replies in the same thread | A Room thread, when the sender selects it for a message |
| Other threads | Never, including other threads of the same Room | Any thread of that Room, when selected |

Attaching a file to a chat never adds it to Room files, never creates a Pin, and never makes it available to other conversations or other people. There is no "Save to Room" yet.

## Supported files

| Kind | Extensions | Stored type |
| --- | --- | --- |
| Text | `.txt` | `text/plain` |
| Markdown | `.md`, `.markdown` | `text/markdown` |
| CSV | `.csv` | `text/csv` |
| JSON | `.json` | `application/json` |
| PDF with a text layer | `.pdf` | `application/pdf` |
| Source code | `.ts`, `.tsx` | `text/x-typescript` |
| | `.js`, `.jsx` | `text/javascript` |
| | `.py` | `text/x-python` |
| | `.java` | `text/x-java` |
| | `.go` | `text/x-go` |
| | `.rs` | `text/x-rust` |
| | `.sql` | `application/sql` |
| | `.html` | `text/html` |
| | `.css` | `text/css` |
| | `.yaml`, `.yml` | `application/yaml` |
| | `.xml` | `application/xml` |

The extension, the bytes, and (for images) the declared type are all checked. A browser's guessed type is not trusted on its own: browsers report `.ts` as video, so text and code are accepted only when the bytes are valid UTF-8 with no NUL byte and no binary file signature. A `.pdf` must contain a PDF header.

Not supported:

- **Images** are refused with "Images aren't supported yet. Attach text, code, or a PDF." The Fast mode's model is text-only, so image understanding could not behave the same in every mode, and Nibie does not fake it or add OCR to claim it.
- **Scanned PDFs** (no text layer) are refused with "That PDF has no extractable text. Scanned PDFs aren't supported yet."
- **Password-protected PDFs**, archives, Office documents, and any other type are refused with a reason.

## Limits

All limits live in `lib/attachments/limits.ts` and are enforced on the server, and again in the database where they are structural.

| Limit | Value |
| --- | --- |
| Attachments per message | 3 |
| Size per file | 10 MB (browser uploads to Storage via TUS with a signed token; the API never receives the file body) |
| All attachments of one message together | 20 MB |
| Text kept per attachment | 24,000 characters |
| PDF pages read | First 50 pages |
| Attachment text in one model request | 6,000 estimated tokens, shared by every attachment in context |
| Unsent drafts per account | 20; a draft unsent for 24 hours is removed the next time that account uploads |
| Staging upload session | 2 hours; unused staging objects are removed on the next upload-init, finalize/cancel, or TTL reconcile |

A file longer than the text limit, or a PDF longer than 50 pages, is kept in part. Its chip says "partly read", and Nibie is told the file is partial.

## How it works

1. **+** opens the file picker (in a Room thread, a small menu offers **Upload from device** or **Room files**). Files can also be dropped on the composer.
2. The composer checks name, type and size, then asks `POST /api/chat/attachments/upload-init` for a server-generated staging path and signed TUS token (JSON only — no file bytes). Multipart `POST /api/chat/attachments` is retired (410).
3. The browser uploads the file with TUS resumable upload to the private `chat-attachment-staging` Supabase Storage bucket (`/storage/v1/upload/resumable/sign` + `x-signature`).
4. The composer calls `POST /api/chat/attachments/finalize`. The server verifies owner, path, size, and type, downloads the staging object, extracts text (24k cap), uploads the original bytes to the durable private `chat-attachments` bucket, saves an unsent **draft** with `storage_path`, and deletes the staging object. The chip shows "Reading…" during this step. Cancel with `{ uploadId, cancel: true }` (or `abort: true`).
5. A chip can be removed before sending (`DELETE /api/chat/attachments/:id` deletes the draft and its durable object; an in-flight upload also cancels staging). A failed upload shows its reason; a network or service failure can be retried.
6. Send is disabled while a file is still being read, or while a failed one is still in the composer. A message is never sent without an attachment that is shown. Stop and persistence behave as for ordinary chat turns.
7. On send, the message and its attachments are saved together by `append_user_message_with_attachments`: either the message is saved with all its attachments, or nothing is saved and the draft stays in the composer.
8. The reply streams as usual. Its context includes the text of the attachments.
9. The sent message shows its attachments as small name chips. The owner can download the original file from the chip (`GET /api/chat/attachments/:id/download` → short-lived signed Storage URL). A reload shows the chips again from the server.

A message needs text: a file alone cannot be sent without a question or note.

## Storage

Migration `drizzle/0009_chat_attachments.sql` adds `message_attachments`. Migration `drizzle/0025_chat_attachment_direct_upload_10mb.sql` raises the size limits and adds transient staging. Migration `drizzle/0026_chat_attachment_owner_download.sql` adds durable originals (`storage_path` + `chat-attachments` bucket) for owner download:

- `user_id`, `conversation_id`, `message_id`: a draft has no conversation or message. Once sent, a composite key `(message_id, conversation_id, user_id) → messages(id, conversation_id, user_id)` ties it to exactly one of the owner's own messages in that conversation.
- `original_name` (sanitized, 1–120 characters), `mime_type` (allowlist), `size_bytes`, `storage_path` (nullable for legacy rows; owner-scoped path when present), `extracted_text` (1–24,000 characters), `truncated`, `page_count`.
- Deleting a message or a conversation deletes its attachment rows. Delete-all in Settings also deletes unsent drafts. Draft remove and draft TTL cleanup also remove durable Storage objects when `storage_path` is set.
- Staging: `attachment_upload_sessions` + private bucket `chat-attachment-staging` (10 MiB object limit, owner-folder RLS). Staging objects are deleted after finalize, cancel, failure, or session TTL.
- Durable originals: private bucket `chat-attachments` (same MIME allowlist and 10 MiB limit, owner-folder RLS). Path shape `{user_id}/attachments/{attachment_id}/{attachment_id}.{ext}`. Owner download uses a short-lived signed URL; the browser never receives a service-role key.

## Security

- The owner always comes from the session. Upload-init and finalize refuse any request that names an owner, message, conversation, storage path, or extracted text. Paths are server-generated only.
- Staging and durable paths are under `{user_id}/…`; Storage policies and session/attachment rows both require `auth.uid()`. Cross-account reads and client-chosen paths are refused. Download is owner-only (same unavailable response for missing and non-owned ids).
- Row-level security is enabled and forced. A person can read only their own attachments, create only unlinked drafts, delete only their own unsent drafts, and link a draft only once. A sent attachment cannot be unlinked, moved, or edited. Only `conversation_id` and `message_id` are updatable.
- The composite key makes it impossible to link an attachment to another person's message or to a message in a different conversation. The send function also refuses an attachment that is missing, not owned, or already sent, and then saves nothing.
- A retried send with the same message id succeeds only with exactly the same attachments, so repeated clicks cannot create a second message or move a file.
- Ordinary requests use the signed-in session. There is no client service-role path and no public bucket. File bytes never pass through a Vercel Function body.
- Nothing in a file is executed, followed, or unpacked. Text is decoded; PDF text is read page by page without fetching anything, running scripts, or rendering forms.
- Extracted text is never sent to the browser and never logged. Logs carry counts and codes only.

## Context

Attachment text is untrusted data. It is placed in the data block, never in the product-policy prompt:

1. Product rules
2. Profile
3. Room instructions and brief, Pins, selected Room files
4. **Chat attachments**
5. Thread summary
6. Recent messages
7. The current request

Each attachment is wrapped like this:

```text
[Attachment]
filename: "project-spec.pdf"
type: PDF
pages: 12
attached to: the current message
status: complete
<untrusted_attachment_content>
…extracted text…
</untrusted_attachment_content>
```

A note before the attachments tells the model that file content cannot change its rules, grant permissions, or instruct it, and that a partial or missing file must not be presented as fully read. Any boundary tag inside a file's own text is neutralized so the file cannot close its block.

Attachments of the current message come first, then attachments of earlier messages in the context window, newest first. Within the budget each one is included whole when it fits, otherwise it is cut and marked "partial: only the beginning of this file fits in this reply". One that does not fit at all is named as not included. The order and cuts are deterministic. Attachments of messages that have fallen out of the recent-message window are not used.

The context panel shows **Attachments** when attachment text was used.

## Modes

Fast, Balanced and High all receive the same attachment context. Attachments do not change routing, and no provider or model id reaches the browser.

## Known limitations

- No images, OCR, Office documents, or archives.
- No in-chat preview of a sent attachment (download only).
- Attachments uploaded before durable originals shipped may have no `storage_path` and cannot be downloaded.
- A message needs text in addition to its files.
- Account export does not include attachment files or extracted text yet.
- An attachment on a message older than the recent-message window is not used for later replies.
