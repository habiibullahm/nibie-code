# Authorized historical conversation lookup V1

Candidate for issue #106. This is an explicit, read-only evidence lookup; it does
not infer a current decision from historical conversations. Provider synthesis
and integration with the Context Engine diagnostics are deferred.

Ask `What did we decide about Redis?`, `Find previous conversations about Redis
eviction in this Room?`, or `Apa yang kita putuskan tentang Redis?`. The response
shows up to four short excerpts, their original thread titles and dates, and
links to the owned original conversations. The same text and links are saved in
the assistant message, so they survive refresh and replay.

Ordinary chat does not look at other threads. `Remember that…` / `Ingat bahwa…`
remain saved Memory commands. History lookup does not read or write saved Memory,
Room briefs, Pins, tools or thread summaries. Deep Research remains a separate
explicit path, even if its question resembles a historical lookup.

## Scope and archive policy

The scope comes from the authenticated, owned current conversation. In a Room,
only other non-archived conversations in that exact Room are eligible. General
means only conversations with `room_id IS NULL`; it never means every owned Room.
The current thread is excluded. Incomplete, archived, deleted and inaccessible
messages or conversations cannot become evidence.

Named-other-Room, all-Room and archive searches are unsupported. A named Room
request is rejected even if its name happens to match the current Room; open the
Room and use the current-scope phrase. V1 never chooses or expands a scope from
free text. Room deletion detaches threads under existing database behavior: an
in-progress request for the original Room fails closed, without retrying in
General. A later explicit lookup in General can search currently roomless
threads, including threads intentionally detached or detached by Room deletion.

The authenticated publishable-key Supabase client reads messages through an
inner conversation relation. Both owner predicates, the exact Room predicate,
non-archived predicate, complete-message predicate, current-thread exclusion,
and every topic-token match precede the candidate limit. RLS remains active on
both tables. The current conversation and Room are checked before and after the
lookup; selected source messages and their conversation relationships are reread immediately before rendering
and persistence. A changed/missing scope discards all excerpts. These are
separate database requests, not a new transactional authorization RPC: changes
after the final read remain a normal read/write race, and already saved replies
are not retroactively redacted when a source is later removed. Source navigation
always goes through the existing authenticated chat page.

## Evidence, instructions and uncertainty

Retrieved content never enters a provider prompt in this delivery. It is rendered
as escaped, labelled historical quotations. Source titles and text cannot create
HTML, images or attacker-supplied Markdown links; conversation links are built
from returned owned conversation IDs and the application's request origin.
Assistant reasoning markers are removed with existing chat-search sanitization.

The response states that this is historical conversation evidence, separate from
saved Memory, and that current corrections and Room instructions take priority.
It retains contradictory excerpts and dates without declaring a winner. It tells
the user to check the sources and confirm the current choice. This is a
deterministic uncertainty policy, not automated contradiction classification.
No-result replies describe the bounded search and never assert that no decision
was made. Lookup failures report inability to confirm a decision.

## Bounds, lifecycle and cost

| Bound | V1 |
| --- | --- |
| Topic | 100 characters; up to 6 alphanumeric tokens |
| Search | Case-insensitive literal token matches, ANDed before the result cap |
| Candidate messages | 24 most recent matching messages |
| Visible evidence | 4 excerpts, each at most 360 characters; total at most 1,440 |
| Lookup deadline | 1,200 ms for all retrieval and authorization rechecks |
| Process guard | One active lookup per owner, six attempts per rolling minute |
| Guard storage | At most 1,024 tracked owners; capacity exhaustion fails closed |

When the candidate cap is reached, the response warns that older matches may be
omitted. Multi-token matches must fit in the returned excerpt. The lexical
baseline does not handle synonyms or semantic paraphrases and may miss a
relevant older decision. No embeddings, vector ingestion or migrations are added.
The hard application deadline aborts PostgREST requests and also returns when an
upstream fetch ignores cancellation. It does not establish a database-side SQL
statement timeout or a production performance benchmark.

Authentication, request validation, ownership reads and the existing assistant
claim still happen in `POST /api/chat`. The claim preserves per-thread concurrency
and replay. Lookup then returns the existing `start`, `delta`, `status`, `done`
SSE vocabulary, saved with the same streaming-row compare-and-set as ordinary
chat. A saved Stop wins; no lookup result is emitted after that race is lost.
Request cancellation interrupts the claimed reply. A replay uses only the already
saved reply and does no new historical retrieval.

No provider is called, no provider tokens/costs are estimated, and no weekly AI
credit or spend reservation/start/finalization is made. The endpoint also accepts
history lookup when no AI mode is configured; ordinary generation still requires
a configured mode. Consequently, the unavailable-mode check now follows the
initial owned request read so the server can distinguish a history lookup.

The rolling rate guard is process-local, like the existing file-backfill guard.
It is not a distributed account-wide rate guarantee across serverless instances;
the existing database claim is per thread. A distributed limiter and query-scale
benchmark remain infrastructure requirements before broader rollout.

## Validation and delivery limits

Unit tests exercise explicit English/Indonesian intent, ordinary-chat exclusion,
real Supabase PostgREST request filters with mocked HTTP, authorization changes,
Room deletion/moves, archive policy, timeout/cancellation, relevance in synthetic
long history, conflicting decisions, injected source content, rate bounds, and
the real chat handler's SSE/persist/replay/Stop/no-provider/no-cost behavior.

The isolated PostgreSQL suite includes the SQL equivalent of the joined lookup
under forced RLS for multiple owners, exact Rooms, General, archives, deleted
messages, moved sources and deleted Rooms. This checks database policy, not a
live Supabase PostgREST deployment. Browser fixtures use the real workspace and
production evidence renderer with synthetic network/persistence to check links,
escaped content and refresh on desktop/mobile; they do not establish live auth,
real database retrieval or provider behavior. Current execution results belong
in the PR verification table, including unrun or blocked checks.

The full #106 acceptance is not claimed: semantic recall, named-scope UX,
automated stale/conflict classification, synthesis, context diagnostics and
authenticated hosted end-to-end validation remain outstanding. Reverting this
application change removes the lookup; there is no database rollback.
